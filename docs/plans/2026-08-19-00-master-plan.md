- 05b 必须最后（所有功能定型后一次重构到位）。

## 3. Stage 划分

### Stage 0：基线准备（~0.5 天）

- 采集 **before 基线数据**（所有对照实验与简历量化点的对照组）：
  - 启动耗时（启动 → 首个 200 响应）；
  - 大文档处理四阶段耗时（选 1-2 篇 ≥200 chunk 的文档固定为基准文档）；
  - 内存/存储占用（进程 RSS、PG 表体积）；
  - 检索质量抽样（固定 20 个查询的命中情况）。
- 分支策略：main 保持可用，每个 Stage 开 feature 分支（如 `feature/stage1-perf-startup`）。

### Stage 1：性能与启动（01 + 04 独立项 + 07 基础设施）

顺序：**07 基础设施先行**（audit_log 表 + audit 服务队列管道 + request_id/兜底中间件 + 查询 API 基础版——为后续所有 Stage 的埋点提供地基）→ **04 独立项**（参数热读 / O(n²) 修复 / 死代码删除，同步埋 `process.*` 事件）→ **01-C**（分词 TEXT+LZ4 落 PG + 批量按需分词）→ **01-B**（并发预热 + readiness 门控）→ **01 §7.1**（BM25 LRU）。
穿插：**05a 批次 1**（功能 bug 1-4、console 清理、auth.js 死代码、API_BASE）。
验收：文档 01 §6（7 项）+ 文档 04 §6，对照 Stage 0 基线出量化报告。

### Stage 2：适配器架构（02 → 03）

顺序：**02 切割适配器**（含 KB 表迁移 + 三级解析，同步埋 `kb.*` 事件）→ **03 增强适配器**（EnhancerPipeline + CombinedEnhancer，同步埋补生成事件）→ **质量对照实验（03 §7 三组 A/B/C）通过后**切换默认路径 → **显性补生成**（缺口检测接口 + 提示条按钮，埋 `process.generate.missing` 事件）。
穿插：**04 剩余项**（摘要/子问题嵌入并行，随 03 pipeline 落地）+ **05a 批次 2**（配置分组保存、流式渲染节流）。
验收：文档 02 §6 + 文档 03 §6/§7。

### Stage 3：自进化 RAG（06）

- **Phase 1（FAQ 闭环）**：PG `faq`/`kb_share`/`faq_pr` 表 + Milvus `faq` 集合 + 检索前置 FAQ 召回 + 失败检测状态机 + 补全写回（含克隆/PR 双路径）+ 热度/阈值升格（按 KB 归属取 2/3）+ 库主审核升格。**记忆/分享/克隆/PR 全事件随编码同步埋点**。
- **Phase 2（实体图谱）**：EntityEnhancer + entities/relations 集合 + graph 检索策略。
验收：文档 06 §9（11 项，含 KB 可见性隔离 / 共享聚合 / 按 KB 归属双阈值时序 / 克隆路径 / 全局入口不污染 / PR 审核闭环）。

### Stage 4：审计全局验收 + 大批量测试

- **07 全局检查验收**：走查文档 07 §2 事件目录全部操作无漏记、request_id 串联正确、脱敏有效、权限过滤正确（07 §9 六项）——此时埋点已随 Stage 1-3 积累三个 Stage 的真实事件，验收即查真实数据；审计前端页面（功能版）在本阶段补齐。
- **大批量测试**（用户目标：整改后进行）：批量文档导入压测（百级文档）、并发检索压测、自进化闭环连续运行——全部事件进审计中心，观测指标（04 §3.6）汇总为最终量化数据。
验收：文档 07 §9 + 压测报告（吞吐/延迟/成功率/资源占用）。

### Stage 5：UI/UX 整合优化（05b，最后）

- 入口条件：Stage 1-4 全部验收通过。
- 内容：主题修改、比例调整、页面重构、新功能 UI 完整适配（KB 策略选择 / 补生成 / FAQ 管理 / 审计中心完整版 / 检索漏斗可视化）——详见文档 05 §7。
- 执行：重跑浏览器实测旅程刷新问题清单 → 信息架构 → 主题比例 → 细节打磨，每层截图对比、用户确认。
验收：文档 05 §6 + 前后截图对比。

## 6. 实施纪律

- **验收原则（2026-08-19 用户定案）**：每个部分的验收核心是四个「真实」——**是否真实提高性能（最关键）、是否真实优化架构、是否真实可拓展、是否真实合理**。不接受「看起来做了」的整改：性能项必须对照 Stage 0 基线给出实测数据；架构项必须通过对应文档的验证章节（如 03 对照实验、06 可见性/PR 闭环）；**任何一项出现问题时，暂停实施、携带数据询问用户**，不擅自绕过或降级目标。
- **分支策略（用户定案）**：main 分支保持不被污染，每个 Stage 新建 feature 分支实现；因当前只有本地环境无线上环境，是否合回 main 无强制要求（默认每个 Stage 验收通过后合入，保持 main 可演示）。
- 每 Stage 一分支；每项整改完成 → 按对应文档「验证方式」章节逐项执行 → 向用户汇报（含数据）→ 合并。
- 设计文档随代码同步更新（/updateDocs）；实现与设计偏差超预期时，先改文档经确认再改代码。
- 质量门槛不可跳过：03 的对照实验、06 的 KB 可见性/PR 闭环验证、07 的无漏记验证是硬性准入。
- 基线数据（Stage 0）一经采集不再变更方法，保证前后可比。
